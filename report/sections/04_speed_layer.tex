
\section{Speed Layer : Détection en temps réel}

La \textit{Speed Layer} représente la partie temps réel de l'architecture Lambda adoptée dans le projet RAPID. Son rôle est de traiter les journaux de cybersécurité dès leur arrivée dans le flux Kafka, afin de produire rapidement des alertes exploitables par la couche de visualisation et par l'API REST. Contrairement à la \textit{Batch Layer}, qui travaille sur l'ensemble historique des données, la \textit{Speed Layer} se concentre sur les événements récents et sur la détection rapide des comportements suspects.

Dans notre implémentation, cette couche repose principalement sur trois composants :
\begin{itemize}
    \item \textbf{Kafka}, utilisé comme bus de messages pour transporter les journaux de sécurité en continu ;
    \item \textbf{PySpark Structured Streaming}, utilisé pour consommer les messages Kafka, les analyser par micro-lots et appliquer les règles de détection ;
    \item \textbf{Cassandra}, utilisée comme base NoSQL pour stocker les alertes et les résultats temps réel avec une faible latence.
\end{itemize}

\subsection{Ingestion des journaux avec Kafka}

Les journaux de cybersécurité sont publiés dans le topic Kafka \texttt{cybersecurity-logs}. Chaque message correspond à un événement réseau ou applicatif contenant plusieurs champs, comme l'adresse IP source, l'adresse IP destination, le protocole, l'action, le type de journal, le chemin demandé, l'agent utilisateur, le label de menace et le volume de données transférées.

Le topic Kafka est partitionné afin de permettre une consommation parallèle. Cette organisation améliore le débit de traitement et permet à Spark de lire les données de manière distribuée. Les offsets Kafka ont été vérifiés à l'aide de l'outil \texttt{GetOffsetShell}. Cette vérification permet de confirmer que les messages sont bien injectés dans Kafka et que les offsets augmentent au fur et à mesure de l'arrivée des données.

\subsection{Traitement temps réel avec PySpark Structured Streaming}

Le traitement temps réel est réalisé avec PySpark Structured Streaming. Spark se connecte au topic Kafka, lit les messages sous forme de flux continu, puis les transforme en DataFrame structuré. Les messages Kafka sont initialement reçus sous forme de chaînes JSON. Ils sont ensuite parsés pour extraire les champs nécessaires à l'analyse.

Le principe général du pipeline est le suivant :
\begin{enumerate}
    \item lecture des messages depuis Kafka ;
    \item conversion du champ \texttt{value} en chaîne JSON ;
    \item extraction des champs du journal ;
    \item application des règles de détection ;
    \item agrégation par adresse IP et par fenêtre temporelle ;
    \item écriture des résultats dans Cassandra.
\end{enumerate}

La commande \texttt{spark-submit} est exécutée avec les dépendances nécessaires pour Kafka et Cassandra. Les connecteurs utilisés permettent à Spark de lire depuis Kafka et d'écrire directement les résultats dans les tables Cassandra du keyspace \texttt{cybersecurity}.

\subsection{Détection par signatures}

La première famille de règles concerne la détection par signatures. Cette méthode consiste à rechercher dans les champs textuels du journal des indicateurs connus d'attaques ou d'outils offensifs. Les champs les plus importants pour cette détection sont :
\begin{itemize}
    \item \texttt{user\_agent}, qui peut révéler l'utilisation d'outils comme \texttt{sqlmap} ou \texttt{Nmap Scripting Engine} ;
    \item \texttt{request\_path}, qui peut contenir des chemins sensibles comme \texttt{/admin}, \texttt{/login}, \texttt{/wp-login.php}, ou des charges utiles suspectes ;
    \item \texttt{threat\_label}, qui permet de distinguer les événements bénins, suspects et malveillants.
\end{itemize}

Cette détection est utile pour identifier rapidement des comportements typiques d'un scan, d'une tentative d'injection SQL ou d'un accès à des ressources sensibles. Les événements détectés sont stockés dans la table Cassandra \texttt{signature\_alerts}. Chaque alerte conserve l'adresse IP source, l'horodatage, la raison de la détection, le chemin demandé, le label de menace et l'agent utilisateur.

\subsection{Détection de brute force}

La deuxième règle de détection concerne les attaques de type \textit{brute force}. Une attaque brute force consiste à répéter un grand nombre de tentatives d'accès afin de deviner un mot de passe, trouver un point d'entrée ou forcer une authentification.

Dans notre traitement, la détection repose sur une agrégation par adresse IP source et par fenêtre temporelle. Le principe est de compter les événements échoués ou bloqués associés à une même adresse IP dans une fenêtre courte. Lorsqu'une adresse IP dépasse un seuil défini, elle est considérée comme suspecte.

Le seuil utilisé dans les tests est :
\begin{itemize}
    \item \textbf{5 tentatives ou plus} ;
    \item dans une fenêtre d'environ \textbf{1 minute} ;
    \item pour une même adresse IP source.
\end{itemize}

Lorsqu'une IP dépasse ce seuil, une alerte est produite avec le nombre de tentatives, la dernière date observée, le type d'attaque et un score de menace. Les alertes sont stockées dans la table Cassandra \texttt{realtime\_threats}.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.95\textwidth]{\detokenize{figures/Speed Layer- Hamza/Screenshot 2026-05-13 195824.png}}
    \caption{Exécution du module de détection des attaques brute force.}
    \label{fig:speed-bruteforce-detection}
\end{figure}

Les captures montrent que certaines adresses IP dépassent le seuil défini. Par exemple, une IP ayant 5 tentatives reçoit un score de 50, tandis qu'une IP ayant 6 ou 7 tentatives reçoit un score plus élevé. Cette logique permet de classer les alertes selon leur gravité.

\subsection{Détection des volumes anormaux}

La troisième règle concerne la détection d'un volume de trafic anormal. Ce type de détection est important pour repérer des comportements comme :
\begin{itemize}
    \item une exfiltration de données ;
    \item un transfert massif inhabituel ;
    \item une activité réseau excessive depuis une même adresse IP ;
    \item un comportement automatisé générant un trafic élevé.
\end{itemize}

Avant de fixer le seuil, un script de test a été utilisé pour analyser un échantillon de messages Kafka. Ce test a permis d'estimer le volume moyen par message, le volume maximum, le nombre moyen de messages par IP et les IP les plus consommatrices en bande passante.

À partir de cette analyse, une recommandation de fenêtre et de seuil a été établie. Le système utilise une fenêtre temporelle de 10 secondes et un seuil d'environ 3012 Ko. Cela signifie qu'une adresse IP est signalée si elle dépasse ce volume dans une fenêtre de 10 secondes.

Lors de l'exécution du traitement, Spark calcule le total des octets transférés par adresse IP et par fenêtre temporelle. Si le total dépasse le seuil, une alerte est créée et stockée dans la table Cassandra \texttt{volume\_alerts}. Cette table conserve l'IP source, le début et la fin de la fenêtre, le volume total, le seuil utilisé et la raison de l'alerte.

\subsection{Calcul du score de menace}

En plus des alertes spécifiques, la \textit{Speed Layer} calcule un score de menace par adresse IP. Ce score permet de synthétiser plusieurs indicateurs dans une seule valeur numérique. Il facilite ensuite le classement des IP les plus dangereuses dans le tableau de bord.

Les principaux indicateurs utilisés sont :
\begin{itemize}
    \item le nombre total d'événements associés à l'adresse IP ;
    \item le nombre d'alertes par signatures ;
    \item le nombre d'événements suspects ;
    \item le nombre d'événements malveillants ;
    \item la présence d'alertes brute force ;
    \item le volume de trafic généré.
\end{itemize}

Le score final est stocké dans la table Cassandra \texttt{threat\_scores}. Cette table permet à la couche API et au tableau de bord de récupérer rapidement une vue synthétique des IP les plus risquées.

\begin{figure}[htbp]
    \centering

    \caption{Calcul des scores de menace par adresse IP.}

Cette approche rend la détection plus lisible. Au lieu de présenter uniquement des événements bruts, le système fournit une information agrégée et exploitable, ce qui facilite la priorisation des investigations.

\subsection{Stockage temps réel dans Cassandra}

Cassandra a été choisie pour la \textit{Speed Layer} car elle est adaptée aux écritures fréquentes et aux lectures rapides sur de grands volumes de données. Dans notre cas, Spark écrit régulièrement des micro-lots de résultats dans Cassandra. Chaque table est conçue selon le type de requête attendu par l'API et le tableau de bord.

Le keyspace utilisé est \texttt{cybersecurity}. Les tables disponibles sont :
\begin{itemize}
    \item \texttt{logs} ;
    \item \texttt{realtime\_threats} ;
    \item \texttt{signature\_alerts} ;
    \item \texttt{threat\_scores} ;
    \item \texttt{volume\_alerts}.
\end{itemize}

\subsection{Synthèse}

La \textit{Speed Layer} permet donc à RAPID de passer d'une simple collecte de journaux à une analyse temps réel exploitable. Kafka assure l'ingestion continue, Spark applique les traitements de détection par micro-lots, et Cassandra conserve les résultats dans des tables adaptées aux besoins de consultation rapide.

Les trois familles de détection mises en place couvrent des scénarios complémentaires :
\begin{itemize}
    \item la détection par signatures pour identifier les outils et motifs d'attaque connus ;
    \item la détection brute force pour repérer les tentatives répétées depuis une même IP ;
    \item la détection de volume anormal pour surveiller les transferts excessifs.
\end{itemize}

Cette couche est essentielle dans l'architecture globale du projet, car elle fournit des alertes quasi immédiates et alimente directement les composants de visualisation et d'API.
